# Gestion Malo — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Intégrer le parcours MR → PCM → cuves ensemencées avec sélection des lots/analyses et des intrants en stock, dose saisie avec défaut 4 %, mouvements atomiques et historique durable.

**Architecture:** Un dossier persistant référence deux lots de préparation indépendants. Les volumes, analyses, événements et stocks réutilisent les tables existantes ; le module Malo crédite les lots cibles existants lors d'une incorporation. Des composants spécialisés servent la préparation, les contrôles et la distribution dans l'onglet Malo.

**Tech Stack:** Next.js App Router, React, TypeScript, Prisma/PostgreSQL, Zod, node:test et Playwright, sans nouvelle dépendance produit.

**Spec:** [Spécification validée](../specs/2026-10-08-malo-design.md), incluant les libellés Bactéries/Activateur/LSA et **+ Ajouter un produit**.

## Global Constraints

- L'onglet **Malo** est placé dans Œnologie entre Tour de FA et Assemblages.
- Le pourcentage d'ensemencement est saisi par l'utilisateur, avec **4 % prérempli** à la création du dossier.
- La base du pourcentage est le **volume du lot destinataire avant ajout**.
- Aucun mouvement ni qualification automatique ne découle d'un calendrier ou d'un critère atteint.
- Conserver les libellés génériques du schéma : **Bactéries**, **Activateur**, **LSA**.
- Un bouton **+ Ajouter un produit** permet d'ajouter des écorces de levures ou tout autre intrant réellement utilisé.
- Les volumes en base restent exclusivement ceux des lots ; aucune duplication dans le dossier.
- Les calendriers restent séparés ; les quantités non documentées restent à renseigner.
- Toutes les références sont limitées à l'organisation de la session ; écritures pour ADMIN/CHEF_CAVE/CAVISTE.
- Transactions sérialisables, UUID réutilisé après réponse inconnue, aucune nouvelle tentative avec une nouvelle clé tant que le résultat demeure inconnu.
- Migration additive ; aucune classification historique à partir du nom d'une cuve ; aucun déploiement dans ce chantier.

## Review Focus

- Un SO₂ ou malique mesuré à zéro reste une mesure, jamais une absence : tâche 3.
- Une analyse importée après dilution mais prélevée avant celle-ci ne peut qualifier le nouveau mélange : tâche 3.
- Un intrant choisi deux fois ou en g/kg ne doit pas permettre un double dépassement de stock : tâche 4.
- Une cuve comportant plusieurs lots ou un compartiment ne permet ni choix implicite du lot cible ni dépassement de capacité : tâches 2 et 5.
- Le cycle PCM → MR → PCM forme une généalogie avec retour : consultation terminée et débits exacts, tâches 5 et 8.

Contrats exportés dans `lib/malo-types.ts` :

```ts
type MaloRole = 'MR' | 'PCM';
type MaloProductRole = 'BACTERIES' | 'ACTIVATEUR' | 'LSA' | 'AUTRE';
type MaloProductInput = {
  productId: number; role: MaloProductRole; label?: string;
  quantity: number; unit: 'g' | 'kg' | 'L' | 'hL';
  addedVolumeHl: number; // 0 pour solides ; volume réel déclaré pour liquides
};
type MaloSnapshot = {
  lotId: number; volumeHl: number; status: string;
  compositionEventId: number | null; lastMutationEventId: number | null;
};
type MaloRecipe = {
  sources: Array<{ lotId: number; volumeHl: number; expectedVolumeHl: number }>;
  waterVolumeHl: number; products: MaloProductInput[];
};
type MaloDestinationInput = { lotId: number; snapshot: MaloSnapshot; volumeHl: number };
type MaloControlResult = {
  consumptionPct: number | null; criterionReached: boolean;
  reason: 'REFERENCE_MANQUANTE' | 'CONTROLE_MANQUANT' | 'CONTROLE_PERIME' | null;
};
type MaloOperationResult = { eventId: number; preparationId: number };
```

Le contexte analytique typé `extraData.malo` contient `schemaVersion: 1`, `preparationId`, `role`, `containerId`, `sampledAt` et `compositionEventId`. Les mesures utilisent les clés déjà connues `malique`, `sucresResiduel`, `aciditeVolatile`, plus `temperatureC` et `density20` si explicitement corrigée, ou `density` sinon. `analysisDate` reçoit le prélèvement réel pour ces analyses. Une confirmation d'homogénéisation est un événement distinct, lié à la composition courante ; l'ID de cet événement ne remplace pas `compositionEventId`.

## Handoff et revue

Ce plan couvre un seul parcours métier ; les tâches suivent les dépendances des contrats et des transactions. L'exécution native dans cette session est recommandée : dossiers, contrôles, événements et vues partagent les mêmes interfaces, et leur intégration gagne à rester cohérente au fil des tâches. L'autre option est une exécution avec sous-agents et revues indépendantes par tâche, si l'utilisateur choisit cette méthode. Ne commencer aucune des tâches avant relecture du plan et choix du mode d'exécution.

Avant exécution, appliquer la compétence worktrees pour décider de l'isolation et préserver le contexte de travail existant. La revue finale suit les compétences de revue et vérification ; ne pas annoncer de migration appliquée, de tests SQL passés ou de déploiement sans preuve correspondante.
